# METHOD — 6단계로 데이터 문제를 설계하고 검증하기

사람이 검토하고 확정하는 설계 틀이다. AI는 표 초안과 단계별 구현을 돕고, 업무 기준·합격 문장·사람의 이해를 대신 결정하지 않는다. 특정 조직의 표준이나 품질 인증을 정의하는 문서는 아니다.

한 줄 원칙: **읽기 → 정규화 → 정제 → 판정 → 순위/집계 → 표시.**
이름은 논리적 책임이다. 파일·클래스를 여섯 개 만들라는 뜻이 아니다. 프로젝트의 기존 src/·실행법·필수 제출 구조를 우선한다.

## 0. 기존 하네스와 연결 — 무엇을 언제 쓰는가

| 구분 | 질문 | 기록 |
|---|---|---|
| 기존 7 STATE | 지금 발굴/합의/구현/검증/수용/제출 중 어디인가? | state.md: DISCOVERY→CONTRACT→SCAFFOLD→E2E_V0→VERIFY→ACCEPT→SUBMIT |
| 새 6처리단계 | 이 입력이 어떤 변환을 거쳐 결과가 되는가? | skeleton.md: 단계별 입력·출력·정책·근거 |
| 요구사항 | 무엇이 되어야 완료인가? | requirements.md의 REQ-ID·합격 문장 |
| 정책 결정 | 누가 무엇을 확인했고 왜 바꿨나? | interview.md의 답 원문 → decisions.md의 D-ID |
| 실행 증거 | 실제로 무엇을 검사했나? | checks.json의 명령 → 실제 로그·exit code |

두 단계 체계는 서로 대체하지 않는다. E2E_V0에서도 여섯 처리단계를 얇게 통과하고, VERIFY에서는 같은 단계들을 깊게 검사한다. 기존 evaluate/promote/bundle은 독립 fde/work 후보용이다. 바깥 src/는 해당 프로젝트의 검사·지정 구조로 제출한다.

docs/QUICKCARD.md의 시간표는 집중 세션 예시다. 실제 프로젝트의 합의 일정이 우선이다. 이 문서 때문에 새 구간이나 추가 문서 작성 시간을 만들지 않는다. 저장소에서는 docs/METHOD.md·fde/templates/skeleton.md, 설치 후에는 fde/docs/METHOD.md·fde/work/skeleton.md를 쓴다. 설치하지 않으면 지정 PLAN/WORKLOG 안에 짧은 표로 합쳐도 된다.

## 1. 사람이 소유할 세 가지와 기록의 원본

1. **뼈대:** 단계 입력·출력 계약과 작은 실제 입력의 흐름. AI 초안을 사람이 확인한다.
2. **결정:** 담당자 답과 영향 범위. 질문·답 원문은 interview.md 한 곳에 보존하고 D-ID에서 참조한다.
3. **합격 기준:** requirements.md의 `[조건]일 때 [대상]은 [결과]여야 한다`. skeleton에는 REQ-ID와 검증을 연결한다.

모든 문서에 답·기준 전문을 중복 복사하지 않는다. 사람의 사전 예측·직접 코드 추적·내 말 설명은 사람이 먼저 작성한다. AI가 만든 문장에는 초안임을 표시하고 사람의 실제 행동처럼 기록하지 않는다.

각 단계에 입력/출력·함정·D-ID·정책 위치·합격 REQ·검증·화면/파일 근거를 연결한다. 다음 단계는 이전 단계의 명시한 출력을 사용하며, 설정·마스터·기준 시각·원문 참조 같은 공통 입력도 계약에 적는다. 원본 CSV를 단계마다 몰래 다시 해석하지 않는다.

## 2. 여섯 처리단계

| 단계·확인할 질문 | 출력 계약 | 함정·담당자 확인 | 작은 검증과 근거 |
|---|---|---|---|
| 1 읽기: 빠짐없이 들어왔나? | 원본 문자열 레코드 + 파일·레코드 ID·추적 가능한 행 위치 | BOM/인코딩, 따옴표 안 쉼표·줄바꿈, 헤더, 경로. 지원 형식과 실패 처리 명시 | 표준 CSV 파서 사용. 헤더 제외 논리 레코드 수 확인. 특수 레코드가 분할되지 않는지 검사 |
| 2 정규화: 같은 것을 같게 보나? | 표준 타입·시간대·단위 + raw 값/원문 참조 + 해석 오류 | ID 동일시, 벤더 등급, 무시간대 값, 단위. 정책은 담당자 확인 | 대응표 각 값·UTC/현지 시각 동등성·원문 보존. 오류와 미상은 3단계에서 필드별 합의 정책으로 분류 |
| 3 정제: 불확실한 것을 숨기지 않았나? | 정상 대표 / 격리와 사유 / 중복과 대표 참조 | 중복 키·상충·역전·마스터 충돌. 반복 발생과 재전송은 다름 | 파일별 배타적 건수 보존, 사유별 건수, 원문 추적. 주 화면에 확인 목록 건수 |
| 4 판정: 합의한 업무 조건인가? | 대상별 라벨 + 라벨별 근거·적용 정책 | 시점·포함/초과·계획된 상태·원인 계열·분모. 판정은 결정론적 코드 | 고정 입력/시점에서 담당자가 기대한 사례와 반례, 임계값 양쪽. 등급은 Major→Critical처럼 명칭 표시 |
| 5 순위/집계: 왜 이 순서/숫자인가? | 정렬/집계 결과 + 정렬 키 순서·각 값 또는 분자/분모 | 중요도·우선 조건·동률·별도 그룹. 단순 가중합이 우선 조건을 뒤집는지 확인 | 고정 사례의 기대 순위·동률·그룹 분리 또는 작은 수기 집계. 근거와 실제 정렬 키가 같아야 함 |
| 6 표시: 사용자가 다음 행동을 고를 수 있나? | 프로젝트가 요구한 화면/파일/CLI, 웹이면 필요한 API | 기준 시각·오류·빈 결과·오래된 문구·사용자 문자열 처리 | 실제 입력→출력, 오류 메시지. 웹은 지정 바인딩·포트, API와 화면 일치·문자열 비실행 확인 |

순위가 없는 프로젝트는 5단계를 집계·검색 정렬로 바꾼다. 웹이 아닌 프로젝트에 서버·JSON API를 추가하지 않는다. 마스터·조인이 없으면 관련 검사는 해당 없음으로 남긴다. 모든 일반 함정을 실제 프로젝트의 필수 기능으로 만들지 않는다.

### 건수 보존 — 같은 단위의 배타적 분류만 더한다

`입력 데이터 레코드 N = 정상 대표 V + 격리 원본 Q + 중복 원본 D`

- 파일별 원본 데이터 레코드 기준이다. 헤더·빈 레코드 처리 규칙을 명시한다. 따옴표 안 줄바꿈 때문에 CSV 물리 줄 수와 다를 수 있다. 서로 다른 파일·단계·이벤트·설비 수를 더하지 않는다.
- 모든 원본 레코드 ID는 V/Q/D 중 정확히 한 곳에 들어간다. 중복 레코드는 대표 원본 ID를 참조한다. 키 전체가 상충해 격리되면 그 그룹의 원본 전부를 Q로 보내고 D에도 세지 않는다.
- 경고 태그는 겹칠 수 있지만 분류 건수는 겹치지 않는다. 격리 Critical을 주 화면에 경고로 보여도 정상 V에 다시 더하지 않는다. 정상 대표를 추가 격리했다면 V에서 빼고 Q로 옮긴다.
- 예: 입력 10 = 정상 7 + 격리 1 + 중복 2. 격리 1건을 경고 화면에도 보여 준다고 입력이 11이 되는 것은 아니다.
- 이미 정제한 고유 이벤트 수에 확인 필요 이벤트가 포함돼 있다면 그 표는 이 배타적 분류와 다르다. 이름·단위·포함 관계를 표시하고 식에 그대로 대입하지 않는다.
- 파싱 실패로 파일 전체가 거절되면 입력 건수는 미확정이다. N=0 성공이나 보존 통과로 표시하지 않는다. 조인·확장·집계는 별도로 매칭/미매칭·고유 개체·분자/분모 검증을 한다.
- 채터링·재측정도 실제로 다른 발생일 수 있다. 담당자의 동일 사건 규칙 없이 삭제·중복 제거하지 않는다.

### 시점·분류·안전을 구분한다

발생 이후의 해제 시각이 파일에 있다고 과거 시점에서도 해제로 보지 않는다. 자동 기준의 근거와 직접 선택 여부를 표시한다. 파일의 마지막 정상 관측과 실제 다운로드 시각은 구분한다. 식별·발생 시각·해제 상태의 오류와 등급 미상을 구분한다. 등급만 미상이고 확인된 미해제 조건을 만족하는 기록은 확인 라벨로 유지하며, 격리 여부는 필드별 합의 정책에 따른다. 실제 해제 여부를 확정할 수 없는 오류와 중요한 격리를 주 화면에 노출하는 기준은 담당자에게 확인한다.

사용자 문자열은 화면에서 코드로 실행되지 않도록 출력한다. JSON 값 자체를 무조건 HTML escape하지 말고 HTML로 표시하는 지점과 CSV 수식·셸/SQL 등 실제 출력 경로를 점검한다. 전체 보안을 검증했다고 주장하지 않는다.

## 3. 결정표와 O/X 추적

질문·답 원문은 interview.md의 Q-ID에 두고 아래 표는 decisions.md에서 관리한다. 답변이 길면 원문 근거를 참조하고 문서마다 복제하지 않는다.

| D-ID | 상태 | 결정 (값까지) | 근거 (Q-ID·답 요지) | 영향 REQ | 위치 (config 키·파일:함수) |
|---|---|---|---|---|---|
| D1 | 확인/시범/Unknown/대체됨→Dn | | interview Q-001 | REQ-001 | |

D-ID는 `D1, D2…`처럼 짧게 써서 프롬프트·commit·config 메타데이터에서 그대로 인용한다. 주·영향 처리단계와 검증 결과는 skeleton·requirements에 두고 여기서 중복하지 않는다.

- 초기 발굴은 실제 사례·현재 우회부터 묻는다. 선택지가 명확해진 정책 확인 때는 선택지 + 추천 + 결과·시간 영향을 함께 보낸다. 처음부터 해법을 유도하지 않는다.
- 한 결정은 여러 단계·REQ·검증에 영향을 줄 수 있다. 실제 정책 위치는 설정/상수/인자/함수/문서 중 알맞게 연결한다. 설정 키가 불필요하면 `해당 없음: 이유`로 쓴다. 한 결정당 새 설정·테스트 파일을 억지로 만들지 않는다.
- 결정·REQ·검증의 연결이 없으면 구현 완료를 주장하지 않는다. 자동 테스트로 못 보는 고객 수용·사용성은 실제 확인 증거나 미확인으로 구분한다.
- 답이 바뀌면 새 D-ID로 기록하고 이전 항목에 대체 관계를 남긴다. 영향 REQ·checks·테스트·handoff를 함께 맞춘다. 미확인 정책을 합의된 것으로 표시하지 않는다.
- O = 해당 조건에서 실제 확인한 근거 있음. X = 실패/미실행/미확인과 이유. 제외·해당 없음은 따로 적는다. 정책 승인 O와 결과 수용 O를 별도 열로 둔다. 테스트 수나 REQ 통과 비율을 실제 업무 성과로 환산하지 않는다.

필요할 때 decisions.md의 짧은 O/X 양식을 다음 표로 펼친다. 처음부터 모든 항목을 의무적으로 채우지 않는다.

| REQ·합격 조건 참조 | 결정 D-ID | 정책 승인 O/X·근거 | 구현 검증 O/X·실제 결과·로그 | 결과 수용 O/X·담당자 답 | 실패·미실행·Unknown·제외 이유 |
|---|---|---|---|---|---|
| | | | | | |

## 4. 합격 기준과 작은 반례

요구사항마다 다음 중 관련 항목을 고른다. 고정 입력·기준 시각·설정 버전과 기대값을 함께 정한다.

- 정답 이야기: 합의한 고정 사례에서 대상 A가 우선이다. 다른 입력에서도 A가 항상 1위라는 뜻이 아니다.
- 함정 회피: 단순 건수만 많은 대상 B는 합의한 위험 조건을 이기지 못한다.
- 보존: 원본 레코드 분류와 중복 대표 참조가 맞는다.
- 경계: 포함/초과, 시간 구간·임계값 바로 양쪽을 검사한다.
- 안전·실패: 잘못된 입력·빈 결과를 설명하고 사용자 문자열을 실행하지 않는다.

AI는 확정 문장을 테스트로 옮기고 실제 기대값과 비교한다. 테스트를 통과시키기 위해 합격 문장을 약화하지 않는다. 기준 오류나 담당자 변경이 확인되면 사람이 새 결정을 확정한 뒤 기준과 검사를 같이 바꾼다. 기존 동작이 이미 맞으면 새 테스트가 통과할 수도 있으니 일부러 실패를 만들지 않는다.

## 5. 180분 집중 세션 예산 안에서 사용하는 예시

| 기존 구간 | 이 틀로 할 일 — 추가 시간이 아님 |
|---|---|
| 0~15분 | 0~5 셋업 보호. 5~10 README·공개 입력을 보며 2/3/4단계의 함정 후보를 고르고 10~15 핵심 질문 3~5개 |
| 15~30분 | 기존 범위·검증 준비 시간 안에 skeleton 초안의 필요한 칸만 검토. 각 REQ의 출력 계약·D-ID·기대값을 연결하고 승인 |
| 30~45분 | 여섯 단계를 최소 기능으로 관통. 42~45 첫 실제 결과를 담당자에게 보여 줌. 미확인 정책은 임시·시범으로 표시 |
| 45~115분 | 실패 영향이 큰 단계부터 해당 REQ를 완성. 순서는 고정하지 않음. 76~80 내 코드 추적 후 **80분 구조 동결**, 113~115 두 번째 결과 확인 요청 |
| 115~140분 | 기존 직접 흐름 확인·읽기 전용 위험 리뷰·최소 수정 안에서 단계 경계·보존·근거를 대조 |
| 140분 이후 | 새 기능을 추가하지 않고 기존 회귀·측정·내 설명·fresh run·제출을 수행. 170분 제출 시작 보호 |

기존 정책을 유지한다: 동결 뒤에도 안전·핵심 오류·확인된 필수 변경은 영향과 이유를 남기고 최소 수정·재검증한다. 단순 설정 변경도 결과·순위·회귀에 영향을 줄 수 있으므로 자동 수용하지 않는다.

새 요청은 주 단계/영향 REQ/계약 변경/남은 시간을 확인한다. 충돌 없는 확인된 설정 변경은 관련 검증 뒤 반영하고, 단계 내부 P0 수정은 기존 예산에서 한다. 단계 경계 변경은 80분 이후 기본 보류하되 앞의 필수 예외를 적용한다. 기능 축소가 필요하면 담당자에게 트레이드오프를 확인한다.

UI 15%(180분의 27분)는 선택적 꾸미기에 대한 계획상 상한 참고다. 27분을 새로 더하지 않고 각 기존 구간 안에서 쓴다. 필수 화면·오류·보안·접근성을 버리는 규칙이 아니며 프로젝트 UI 요구가 크면 선택 범위를 먼저 줄인다.

## 6. 단계 단위 위임 프롬프트

```text
[REQ-ID / 주 단계 N]을 작업해. 기존 STATE·지정 src/·시간표를 유지해.
입력·출력 계약: [skeleton 해당 행]. 적용 결정: [D-ID·답 원문 위치].
합격 기준: [requirements의 확정 문장·고정 입력·시점]. 바꾸지 마.
기본 수정 범위: [파일]. 계약/API/공통 테스트 변경이 꼭 필요하면 이유·영향을 먼저 설명하고
확인된 REQ 범위에서 최소 연결 수정해. 미확인 업무 정책은 질문 초안으로 보고해.
관련 테스트 준비 → 현재 결과 확인 → 구현 → 해당 검사·관련 보존식·회귀 실행.
같은 실패 3회면 반복 수정을 멈추고 원인·작은 재현·대안 2개를 보고해.
실행 명령/exit code/통과·실패·미실행/변경 파일/남은 위험을 짧게 보고해.
내 사전 예측·직접 추적·고객 수용을 대신 작성하지 마.
```

git diff --stat과 실제 diff로 범위를 확인한다. 다른 단계 파일이 바뀌었다고 무조건 롤백하지 말고 영향 REQ·계약·검증 근거가 있는지 확인한다. 독립 work 후보만 evaluate/promote를 사용하며 기존 src는 자체 검사를 쓴다. 실제 변경과 근거가 있으면 기존 체크포인트에서 `REQ-ID: 단계 N 요약`으로 로컬 commit한다. 외부 전달·push는 프로젝트에서 승인된 범위를 따른다.

## 7. 다른 데이터 유형과 인수인계에 적용

| 유형 | 정규화·정제의 확인 | 판정·집계의 확인 |
|---|---|---|
| 이벤트·모니터링 | 시간대·코드·재전송과 실제 반복 | 기준 시점 상태·우선 조건 |
| 주문·재고 | 단위·대상 ID·상태 갱신·누락 | 미완료·기한·같은 대상 중복 합산 |
| 품질·측정 | 측정 단위·규격 시점·재측정 | 합의한 경계·정확한 분모 |
| 운영시간 | 상태 코드·겹침·끝 없는 구간 | 계획/비계획·합집합 시간 |
| 문서 검색 | 용어·버전·중복/구버전 | 일치 근거·결과 정렬 |

일반 예시는 질문 소재다. 실제 업무 기준을 담당자와 확인한다. 인수인계에서는 어느 단계에서 무엇을 선택했나(D-ID), 어떤 반례로 확인했나(REQ/로그), 어디서 실패하나(계약/격리), 무엇을 보류했나를 실제 코드와 연결해 설명한다.

단계 마무리 30~60초 확인: 출력 계약 / 결정과 REQ 연결 / 관련 보존·반례 결과 / 근거 표시 / 변경 영향 / 다음 행동. 전체 문서 재작성이나 매 단계 모든 테스트 반복을 의무화하지 않는다.
