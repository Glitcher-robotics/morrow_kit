# STAGE_PROMPTS — 7 STATE별로 필요한 지시 고르기

큰 제목은 state.md/status.py와 같은 **7 STATE**, 그 안의 METHOD ①~⑥은 **데이터 처리단계**다. 예: `STATE: VERIFY / METHOD: ④ 판정 / REQ: <현재 ID>`.
기존 처리 틀에 맞춰 DISCOVERY/CONTRACT/SCAFFOLD/E2E_V0/VERIFY/ACCEPT/SUBMIT마다 산출물·출구 확인과 프롬프트를 연결했다. 점수표·새 상태·추가 필수 절차가 아니다.

**전부 순서대로 보내지 않는다.** 현재 막힌 지점에 필요한 1~2개만 고르고 같은 일을 METHOD/QUICKCARD와 중복하지 않는다. `<...>`는 실제 값, 모르는 것은 Unknown으로 쓴다. 예시를 정답·내 경험으로 복사하지 않는다.

- 시간은 QUICKCARD.md의 180분 집중 세션 예시다. 실제 프로젝트 일정이 우선한다. 0~5분 환경·작업 위치 확인, 15~30 합의, 30~45 최소 흐름, 80분 구조 동결·140분 새 기능 동결·170분 전달 시작을 유지한다.
- **시계는 예산, STATE/GATE는 실제 증거·출구조건이다.** 115분이 됐다고 자동 ACCEPT로 바꾸지 않는다. ACCEPT는 수용 확인 작업 중이라는 뜻이며 고객 수용 O가 아니다. 실패·답 없음·미실행을 그대로 기록한다.
- DIS/CON/SCA/E2E/VER/ACC/SUB는 프롬프트 ID다. 다른 상태에서 같은 질문·검사가 필요해도 사용할 수 있으며 그 때문에 STATE나 시계를 되돌리지 않는다.
- 질문·답 원문=interview Q-ID, 결정=decisions D-ID, 합격 문장=requirements REQ-ID, 계약=skeleton, 검사=checks 또는 지정 프로젝트 명령. 실제 사람 승인 없이 예시 문구로 GATE1을 만들지 않는다.
- 프롬프트 개수·대화·구체값 자체를 성과로 계산하지 않는다. 내 사전 예상과 AI 예상을 구분하며 수용·시각·비교 수치를 만들지 않는다.
- 실제 프로젝트의 허용 도구·데이터·자동화·네트워크·공개/전달 규칙을 확인한다. 제한을 우회하거나 승인 없이 비밀·개인정보를 외부 전송하지 않는다.

## 산출물 읽는 법 — 지정 전달물과 내부 근거 구분

아래 파일은 설치 후 fde/work/의 내부 기록 이름이다. 프로젝트가 지정한 PLAN/WORKLOG/README_RUN·실행 파일의 위치와 형식이 우선한다. 하네스를 설치하지 않거나 문서가 겹치면 같은 근거를 지정 문서의 짧은 표로 합친다. 설치·템플릿 전부 채우기·새 문서 생성 자체가 완료 기준이 아니다.

‘남길 산출물’은 실제 작업의 최소 결과와 근거다. 관련 없는 칸은 이유와 함께 해당 없음, 미확인은 Unknown, 실패·미실행은 X로 남긴다. 담당자 답·내 예측·고객 수용·초기 실패 출력을 사후에 만들어 채우지 않는다. 응답 대기는 0분으로 두고 충돌 없는 작업을 계속하되 결과를 바꾸는 필수 정책의 미확정은 구현·수용 완료로 바꾸지 않는다.

Git은 기존 루트·상태·기준 리비전을 먼저 확인한다. **Git 루트가 없으면 과제 폴더에서 `git init` 후 원본 그대로 `init: 과제 원본`을 commit**하고, 이후 의미 있는 변경을 REQ-ID와 함께 선택 commit한다. 기존 Git이 있으면 재초기화하지 않는다. Git 제한은 기록하고 지정 파일 저장·검증·전달을 우선한다. 보관·전달을 위해 원본 데이터나 사용자 변경을 삭제하거나 꾸며진 이력을 만들지 않는다.

## 고르는 기준

범위 / 근거 / 내가 먼저 쓴 예상 / 멈출 조건 / 실제 증거 중 이번 작업에 필요한 요소를 넣는다.

**실행·변경을 지시할 때는 내 예상 1줄을 붙인다.** 결과를 보면 맞았는지 바로 판정할 수 있게 숫자·순위·실패할 테스트 중 하나를 쓴다. 모르면 `모름 + 이유`로 쓴다. 틀린 예상도 남기고, 결과 뒤에 차이와 원인을 METHOD 단계로 적는다. AI가 내 예상을 대신 쓰지 않는다.

| 쓸모없는 예상 | 판정 가능한 예상 |
|---|---|
| 잘 될 것 같다 | 1위 <대상> <등급>, 2위 <대상> |
| 테스트 통과할 듯 | 새 반례 테스트 1개만 실패, 기존 N개 통과 |
| 건수 맞을 거다 | 입력 N = 정상 a + 격리 b + 중복 c |
| 크게 차이 없다 | 경계 폭 차이 x, 등급이 바뀌는 대상 0개 |

```text
실행 전 내 예상: <숫자·순위·실패할 테스트 또는 모름+이유>. 결과가 다르면 METHOD 단계 번호로 원인을 설명해.
```

## DISCOVERY (0~15분) — METHOD ①②③ 함정·④ 업무 질문

**남길 산출물 — 초안과 확인할 질문**
- [ ] problem.md 초안: 전달/실행 제약, 사용자 결정 한 문장, 성공 기준 후보, 범위/제외/Unknown. 합의 확정은 CONTRACT에서 한다.
- [ ] skeleton.md의 관련 함정 후보와 METHOD 번호. interview.md에 실제 보낸 질문과 받은 답 원문·출처, 미응답 표시. 초기 핵심 3~5개, 전체 후보 최대 7개.
- [ ] decisions.md의 확인된 D-ID 또는 미결 질문 참조. 원문 답을 두 문서에 중복 복사하지 않는다.
- [ ] state.md: `STATE: DISCOVERY`, 실제로 확인한 필수 런타임·작업 위치·Git 기준/제약. 사용하지 않는 Node·패키지 설치 가능성까지 조사하지 않는다.
- [ ] 하네스를 설치한 경우만 보존된 AGENTS 관리 블록·없는 work 템플릿이 준비된다. 미설치면 지정 문서에서 계속한다.
**출구 확인:** 문제/필수 제약과 결과를 바꿀 질문이 보이고 확인/Unknown이 구분된다. 모든 답·초기 commit을 기다리는 조건이 아니다.

DIS-4는 질문을 좁힐 짧은 초안 검토다. 15~22분 문제 정의 구체화 때 다시 써도 되며 새 작업을 추가하지 않는다.

### DIS-5 담당자 질문
```text

먼저 decisions.md를 확인해 이미 결정된 질문은 빼고 D-ID만 인용해. 질문 하나에는 결정 하나만 담아.
```

질문 카드(1질문 = 1결정): `관찰(파일·행·값) → 내 안·추천 → 대안 → 결과 영향 예측 → "맞을까요?"`.

## CONTRACT (15~30분, 실제 승인으로 GATE1) — METHOD ①~⑥ 계약·합격 기준

**남길 산출물 — 구현할 범위와 합격 기준**
- [ ] problem/requirements: 확인된 문제·P0/P1/P2·조건/대상/기대 결과·검사 명령·AI 역할/내 확인 역할. 답 원문 Q-ID와 결정 D-ID 연결.
- [ ] skeleton.md: 이번 핵심 흐름에 필요한 METHOD 입출력·정책 위치·REQ·근거 참조. 불필요한 칸을 억지로 채우거나 설정 키를 만들지 않는다.
- [ ] 독립 work 후보는 checks.json에 REQ와 같은 ID/우선순위/실제 명령, 회귀 1개 이상. 기존 src 프로젝트는 자체 검사와 지정 구조를 쓴다.
- [ ] 측정 입력·대상 범위·명령·기록 위치를 미리 정한다. state.md의 `GATE1 합의:`에는 실제 사람의 범위 승인 근거·실제 시각을 기록한다. 없음은 미승인이다.
- [ ] 로컬 Git이 준비되고 변경이 있으면 27~30분 체크포인트에서 합의 변경을 REQ-ID로 commit한다. 별도 점수용 commit은 만들지 않는다.
**출구 확인:** 본 구현에 필요한 범위·합격 기준을 사람이 확인했고 핵심 정책의 확인/시범/Unknown과 영향이 명확하다. 템플릿의 ‘진행’은 승인 근거가 아니다.

### CON-1 skeleton 계약 검토
```text
내가 검토한 skeleton <경로·행>을 읽기 전용으로 봐. 이전 출력이 다음 입력과 맞는지 확인해.
공통 설정·마스터·기준 시각, raw 참조·격리 사유·라벨 근거의 누락만 지적해.
기존 src 구조·7 STATE를 유지하고 모든 칸·파일 6개를 추가로 강제하지 마.
```

### CON-2 합격 기준 → REQ 합의안
```text
내가 확인한 합격 문장 <원문·고정 입력·시점>을 바꾸지 말고 REQ/우선순위/검증 명령/AI 역할·내 확인 역할에 연결해.
보존식은 같은 파일의 원본 레코드를 배타적 정상/격리/중복으로 분류할 때만 써. 경계·오류·문자열 출력 검사는 관련한 것만 골라.
독립 work 후보면 checks.json의 실제 스키마로 맞추고, 기존 src면 그 프로젝트 검사 명령을 써.
내 실제 범위 승인 근거 <원문 위치 또는 아직 없음>를 확인해. 없으면 합의안까지만 만들고 승인으로 기록하지 마.
```

## SCAFFOLD (30~32분) — METHOD ①~⑥ 실행 경계 확인

**남길 산출물 — 기존 구조에서 실행할 준비**
- [ ] skeleton 또는 handoff에 METHOD↔실제 파일:함수↔실행 명령의 짧은 대응. 기존 코드가 있으면 새 구조를 만들지 않는다.
- [ ] 필요한 입력·정책 위치, 작은 입력과 기대값, 실행할 최소 검사 명령. 설정/상수/인자는 기존 합의와 구조에 맞는 위치를 쓰며 JSON에 주석을 넣지 않는다.
- [ ] 웹이 요구된 경우만 지정 호스트·포트의 진입 위치를 확인한다. CLI/보고서 프로젝트에 서버를 추가하지 않는다.
- [ ] state/handoff에 실행 준비 상태·막힌 것·다음 행동을 짧게 남긴다. 별도 commit은 기존 예산과 실제 변경이 있을 때만 한다.
**출구 확인:** 어디서 어떤 입력·명령으로 최소 흐름을 실행할지 알 수 있다. 빈 함수 여섯 개나 서버 기동 자체를 E2E 성공으로 보지 않는다.

### SCA-1 기존 실행 경계·작은 입력 준비
```text
승인된 REQ <ID>와 skeleton METHOD ①~⑥의 기존 파일·함수·실행 명령 대응을 먼저 확인해.
기존 src가 있으면 구조를 유지하고 대응만 정리해. 필요한 최소 연결만 만들며 함수/파일 여섯 개·config 하나·새 웹서버를 강제하지 마.
작은 입력·기대값·실행 위치를 준비하고 미확인 정책은 표시해. 빈 함수·서버 기동 자체를 E2E 성공으로 기록하지 마.
```
30~32분의 기존 입력·예측 준비 안에서 필요한 것만 한다. 추가 설계 시간을 만들지 말고 실제 관통 결과는 E2E에서 확인한다.

## E2E_V0 (32~45분, 실제 최소 흐름으로 GATE2) — METHOD ①→⑥ 관통

**남길 산출물 — 실제 입력 하나에서 실제 출력 하나**
- [ ] 실제 작은 입력·기준 시각·실행 명령·출력. 합성으로 시작했다면 합성임과 실제 데이터 미검증을 표시한다. 웹이면 필요한 화면/API, 다른 프로젝트면 지정 출력이다.
- [ ] 관련 건수·중복/격리 보존과 작은 판정/집계 기대값 검사 결과. 특정 테스트 개수나 건수 검사만으로 정확성을 대신하지 않는다.
- [ ] 내 실행 전 예상이 있으면 decisions의 예측→실제 대조에 보존한다. 아직 직접 예상/구조 설명을 하지 못했으면 미실행으로 쓰고 과거 기록을 만들지 않는다.
- [ ] 42~45분 첫 결과 메시지와 실제 전달/답 여부. 받은 답은 Q-ID→D-ID로 연결하며 답 없음은 수용 미확인이다.
- [ ] state.md `GATE2 E2E v0:`에 실제 명령·입력/시점·결과·로그 위치. 실패하면 막힌 지점과 작은 복구 계획을 남긴다.
**출구 확인:** 최소 입력→출력과 기대값을 실제 확인했다. 담당자 회신이 없다고 실행 성공을 취소하거나 수용 O로 바꾸지 않는다.

### E2E-1 여섯 처리단계 최소 연결
```text
승인된 REQ <ID>와 skeleton 계약으로 실제 작은 입력→출력을 연결해. 합성이면 실제 입력 미검증이라고 표시해.
확인된 최소 판정·정렬/집계만 쓰고 정책 Unknown은 표시해. 역할은 구분하되 함수·설정 파일 개수를 강제하지 마.
웹 프로젝트일 때만 지정 호스트·포트·API를 연결해. 작은 기대값·관련 보존/정상·오류 검사와 실제 실행 근거를 남겨.
변경 파일/명령·exit code/실제 출력/미실행·위험을 짧게 보고해. 화면 장식은 추가하지 마.
```

### E2E-2 실행 전 내 예상과 대조
```text
내가 실행 전에 쓴 예상: <입력 단위·건수/중복/격리/판정·순위의 기대값과 근거, 모르면 Unknown>.
명령 <실제 명령>을 실행하고 예상/실제/차이/근거를 비교해. 다르면 처리단계와 원본 레코드를 짚어 줘.
내 예측을 사후에 맞춰 쓰거나 관측값을 과거 예측으로 바꾸지 마.
```

### E2E-3 구조 이해 대조 — 76~80분 추적 때도 사용
```text
내가 diff와 코드를 읽고 설명한 흐름: <입력→파일:함수→정책/계산→출력>.
읽기 전용으로 틀린 부분·놓친 경계·필요 이유를 설명 못한 파일만 지적해. 내 설명을 대신 완성한 기록으로 쓰지 마.
```

### E2E-4 첫 결과 확인 메시지 — 42~45분
```text
담당자에게 보낼 3줄 초안: 실제 결과/적용한 확인·시범 정책/이 결과로 판단 가능한지 묻는 질문 하나.
현재 입력·시점·실제 출력 근거 <위치>만 사용해. 실행 실패면 막힌 지점과 작은 복구 계획을 써.
직접 전송하거나 수용 확인을 만들지 마. 내가 전달할게.
```
답은 DIS-6으로 기록한다. 응답 대기로 다음 구간을 멈추지 않는다.

## VERIFY (45~115분, 80분 구조 동결) — 관련 METHOD의 P0·반례

**남길 산출물 — REQ별 구현과 검증 증거**
- [ ] 승인된 P0 구현과 관련 반례·경계·회귀 로그: 실제 명령/exit code/통과·실패·시간 초과·미실행. 처음부터 맞는 검사를 억지로 빨강→초록으로 만들지 않는다.
- [ ] 프로젝트에 관련된 정상/격리/중복·원문 추적·판정 근거·정렬 키/분모·기준 시각. 실제 반복과 상태 오류/등급 미상을 구분한다.
- [ ] 확인된 정책 위치와 D-ID, 새 답의 대체 관계. 기술 상수까지 모두 config로 옮기거나 모든 결정에 새 설정을 만들지 않는다.
- [ ] state/handoff: `STATE: VERIFY`, 기록용 `METHOD: <①~⑥>`, 현재 REQ, 완료 근거/남은 실패/다음 행동. status.py가 METHOD나 수용을 자동 판정하는 것은 아니다.
- [ ] 독립 work면 evaluate의 최신 증거, 기존 src면 자체 검사 결과. 실제 변경은 기존 로컬 commit 체크포인트에 남긴다.
- [ ] 76~80분 내 입력→파일:함수→정책→출력 추적, 80분 구조 동결. 큰 위험을 발견하면 최소 확인·수정하고 정기 리뷰 예산을 추가하지 않는다.
**출구 확인:** P0 충족·관련 회귀와 남은 위험을 실제 결과로 판단한다. 미충족이면 통과 상태로 올리지 않고 VERIFY/예외·복구 계획을 기록한다. 170분 전달 예산은 보호한다.
마감 때문에 SUBMIT 준비로 이동하더라도 이전 P0 실패·미실행은 X로 유지한다. STATE 이동을 REQ 통과나 고객 승인으로 바꾸지 않는다.

VER-1~3은 한 요청으로 묶어도 된다. 실패 영향·선행 조건으로 고르고 모든 METHOD를 정해진 순서로 다시 구현하지 않는다.

### VER-1 단계 범위 위임
```text
[REQ-ID / 주 처리단계 N]만 우선 작업해. 계약 <skeleton>, 결정 <D-ID·답 원문>, 합격 문장 <requirements>, 기본 파일 <범위>다.
계약/API/공통 테스트 연결 수정이 필요하면 이유·영향을 먼저 설명하고 확인된 범위에서 최소 수정해.
미확인 업무 정책이 필요하거나 같은 실패 3회면 반복 수정을 멈추고 작은 재현·원인·질문·대안 2개를 보고해.
관련 합격 검사를 먼저 준비해 현재 결과를 확인하고 실제 증거를 남겨.
```

### VER-2 기준을 확인하는 테스트
```text
REQ <ID>의 고정 입력·시점·기대값으로 검사부터 작성·실행해. 현재 통과/실패와 이유가 합격 기준에 맞는지 설명해.
이미 동작이 맞으면 통과를 그대로 보고해. 문법 오류·환경 문제를 업무 기준 실패로 보거나 억지로 실패를 만들지 마.
기준을 바꿔야 한다면 구현 전에 이유와 새 결정 필요성을 알려 줘.
```

### VER-3 변경 영향 예상·구현·검증
```text
확인된 변경 <REQ/D-ID>을 구현해. 내 사전 예상 <문장 또는 아직 작성하지 못함>과 별도로 AI의 영향 예상을 표시해.
관련 검사·보존식(해당할 때)·회귀를 실행하고 예상/실제·명령/exit code·변경 파일·남은 위험을 보고해.
전체 회귀는 공유 계약/광범위한 영향 또는 최종 후보일 때 실행해. 80분 구조 동결·140분 새 기능 동결 예외는 이유를 기록해.
```

### VER-4 근거·대안 질문
```text
방금 정한 <기준값/방식>의 근거 D-ID·코드·데이터는 어디야? 유의미한 대안 1~2개와 결과 차이를 설명해.
실제 비교한 수치만 쓰고 미실행 대안은 가정이라고 표시해. 업무 정책 근거가 없으면 담당자 확인 질문을 줘.
```

### VER-5 합의와 어긋난 구현 수정
```text
구현 <파일·위치>가 결정 <D-ID·원문>과 다르다고 본 내 근거는 <내용>이야. 먼저 읽기 전용으로 대조해.
불일치가 확인되면 해당 변경만 최소 수정하고 관련 검사를 해. 전체 파일/사용자의 다른 변경을 통째로 되돌리지 마.
```

### VER-6 핵심 함수 설명 확인
```text
내가 함수 <파일:함수>를 읽고 설명하면 <정렬 키·방향·동률·시점·예외에 대한 내 말>이야.
실제 코드와 다른 부분·빈 값/동률/구간 경계만 지적해. AI 설명을 내가 이미 이해한 것으로 기록하지 마.
```

### VER-7 새 답과 의도 갱신
```text
담당자 새 답 원문·출처 <근거>. 새 D-ID로 기록하고 이전 결정의 대체 관계·영향 REQ·단계·남은 시간을 짚어.
계약/설정/코드/테스트/문서 중 실제 바뀔 곳과 트레이드오프를 설명해. 합격 기준 변경은 사람 확인 없이 확정하지 마.
확인된 변경만 반영하고 requirements/checks/테스트/handoff와 관련 검증을 맞춰. 설정 한 줄도 무검증으로 완료하지 마.
```

### VER-8 맥락 저장 — 변경·세션 전환 때 1분
```text
handoff/state에 목표·현재 STATE·진행 REQ/처리단계·완료와 실제 증거·미결 D-ID·실행 명령·다음 3행동만 갱신해.
새 세션이 5분 안에 재개하도록 짧게 써. 모든 문서를 다시 쓰거나 미확인 정책을 완료로 바꾸지 마.
```

### VER-9 발견한 큰 보안·운영 위험의 좁은 확인
```text
이미 발견한 위험 징후 <근거>를 중심으로 실제 관련 입력/크기/경로/출력/오류·권한 문제만 읽기 전용으로 확인해.
영향 순 최대 3개만 파일·위치/재현 근거/영향/최소 수정/미검증 범위로 보고해. 파일 수정·자동 UI 조작은 하지 마.
바인딩은 지정 요구와 대조하고 0.0.0.0 자체를 무조건 취약점이나 보안 보장으로 판단하지 마.
```
사용자 화면은 내가 직접 확인한다. 확인된 큰 위험만 기존 예산 안에서 최소 수정·반례 검사한다.
정기적인 넓은 리뷰를 이 구간에 추가하지 않는다. 정기 리뷰는 ACCEPT의 ACC-7을 120~130분에 사용한다.

### VER-10 격리·오류·보존 확인
```text
REQ <ID>의 합의된 오류 정책으로 원본 레코드/분류/사유/중복 대표를 추적하고 목록·건수 근거를 보여 줘.
파일 전체 읽기 실패는 명확히 거절하고 입력 건수는 미확정으로 표시해. 읽지 못한 행 번호·원문을 지어내지 마.
미등록·등급 미상·실제 반복을 무조건 격리/삭제하지 말고 필드별 정책을 따라. 격리 경고를 정상에 다시 더하지 마.
```

### VER-11 정책 위치 점검
```text
업무 기준값·등급표·기간·계열·정렬 순서가 있는 실제 위치와 D-ID를 짧게 정리해.
설정/상수/인자/함수 중 유지할 사람이 바꾸기 쉬운 한 곳으로 모을 필요가 있는지 제안해. 새 설정 프레임워크는 만들지 마.
JSON에는 주석을 넣지 말고 D-ID 연결은 decisions나 유효한 메타데이터에 남겨. 근거 없는 정책은 Unknown으로 보고해.
```
메타데이터 예: `"_decisions": {"trend_points": "D4", "baseline_wafers": "D3"}`. 코드가 `_` 키를 읽지 않게 하고, 과제가 config 스키마를 엄격히 검사하면 decisions의 위치 칸에만 남긴다.

### VER-12 REQ 완료·로컬 commit
```text
REQ <ID>의 현재 소스와 검사 증거가 일치하는지 확인해. 새 변경·실패·불확실성이 있으면 관련 검사만 재실행해.
명령/exit code/핵심 출력/실패·미실행을 기록하고 정책 승인·검증·결과 수용을 구분해.
기존 체크포인트에서 git status와 실제 diff를 보고 의도한 프로젝트 파일만 선택해 '<REQ-ID>: 단계 <N> 요약'으로 로컬 commit해.
git add -A·Git 재초기화·신원 변경·빈 commit·승인 없는 push는 하지 마. Git 제한이면 기록하고 진행해.
```

## SUBMIT (155~180분) — fresh run·사실 카드·최종 전달

**남길 산출물 — 전달 후보와 실제 완료 확인**
- [ ] 155~160분 실제 전달 위치의 fresh run: 유한 명령 exit code와 서버 준비/HTTP 응답을 구분해 기록. state.md `GATE3 fresh run:`은 실제 검증 결과·로그 위치를 쓴다.

- [ ] 165~170분 사실 카드: 실제 진입 명령·핵심 함수/구조·큰 결정과 대안·검증 범위·제외/한계. 내가 원본과 대조하고 설명한다. 실제 변경이 있으면 169~170분 최종 로컬 commit.
- [ ] 170~180분은 지정 전달 위치·파일·실행법·사용자 확인과 실제 인도에 쓴다. 실제 마감·전달 절차가 이 예시 시간보다 우선한다.

### SUB-1 fresh run — 155~160분

## STATE 전환 체크 — 최소 산출물과 실제 근거

| STATE | 핵심 산출물 | 출구를 판단할 실제 근거 |
|---|---|---|
| DISCOVERY | 문제/제약 초안, 질문·답 원문/미응답, 함정 후보 | 관측·정책·Unknown이 구분되고 중요한 질문을 전달함 |
| CONTRACT | 필요한 계약, REQ·검증·측정 계획, 결정 참조 | 실제 사람의 범위 승인 GATE1. 핵심 미확정을 승인으로 만들지 않음 |
| SCAFFOLD | 기존 파일/함수·실행 명령 대응, 작은 입력·기대값 | 최소 흐름을 실행할 준비. 빈 틀 자체는 성공 아님 |
| E2E_V0 | 실제 입출력·작은 기대값 검사·첫 피드백 요청 | 실제 실행 근거 GATE2, 수용은 별도 확인/미확인 |
| VERIFY | P0·경계/회귀·관련 원본 보존/근거·남은 위험 | 현재 소스의 실제 검사 결과. 실패는 실패로 유지 |
| ACCEPT | 결과 피드백·회귀·필수 문서·조치·내 설명 | 합의와 결과 대조, 수용/Unknown·제외/한계 구분 |
| SUBMIT | fresh run·저장/지정 파일·사실 카드·전달 확인 | GATE3 실행 근거, GATE4 실제 인도·사용 확인 |

시간이 부족하면 장식·중복 기록·선택 범위를 먼저 줄이고 필수 실행·정확성·위험·전달 시간을 보호한다. 불필요한 내부 칸 때문에 마감을 넘기지 않고, 실제 필수 항목의 실패를 문서 축약으로 숨기지 않는다. 해결하지 못한 것은 X/Unknown·영향·다음 개선으로 남긴다.
