# SELFCHECK — 기술·의도·인지 자가 점검

점수는 "했다"가 아니라 **기록에 남았다**로 받는다는 가정으로 점검한다. 축 이름은 공개 평가 항목 기준이고 배점·판정 방식은 공식이 아니다.
**T** 기술(결과물) / **I** 의도(목표·분해·검증·제약·갱신·체계) / **C** 인지(예측·구조 이해·근거 이해).
사용법: ① 프롬프트를 보내기 전 30초 점검 ② 체크포인트마다 2분 점검 ③ 빈칸은 다음 프롬프트에서 바로 채운다. 체크를 채우려고 기록을 지어내지 않는다.

## 1. 매 프롬프트 — 보내기 전 30초

| 축 | 점검 | 예 |
|---|---|---|
| I 분해 | **범위**: 한 REQ·한 METHOD 단계만 맡겼나? 고치지 말 파일을 적었나? | `[REQ-014 / METHOD ③]만. spc.js 외 수정 금지` |
| I 의도 | **근거**: 정책이 걸리면 D-ID를 인용했나? 없으면 질문으로 돌렸나? | `D4·D9 기준으로` |
| C 예측 | **내 예상**: 숫자·순위·실패할 테스트 중 하나로 반증 가능하게 썼나? | `내 예상: 계측 확인 4건, CVD-05 A만 조치` |
| I 검증 | **멈출 조건**: 결정표에 없는 규칙·테스트 수정·같은 실패 3회면 멈추라고 했나? | `없는 규칙이 필요하면 멈추고 질문 초안` |
| I 검증 | **증거**: 테스트 먼저→실패 확인→구현→전체 테스트·exit code를 요구했나? | `실패 출력부터 보여 줘` |

받은 뒤 30초:
- [ ] **C 예측** 예상과 결과를 대조했나? 다르면 METHOD 단계 번호로 원인을 물었나?
- [ ] **C 구조** `git diff --stat`으로 범위를 보고 핵심 함수 하나를 직접 읽었나?
- [ ] **C 근거** 새 기준값·방식이 나오면 "왜 이 값인가, 대안 1~2개와 결과 차이"를 물었나?
- [ ] **C 근거** 결정과 다른 구현이면 D-ID를 근거로 반박하고 되돌렸나?
- [ ] **I 의도** 담당자 답이 새로 생기면 같은 응답에서 interview Q-ID → decisions D-ID에 기록했나?
- [ ] **T 유지보수** REQ가 통과하면 `REQ-xxx: METHOD ④ 요약 (Dn)`으로 commit했나?

## 2. 체크포인트 — 시각은 180분 기준 예시

### 0~5분 시작
- [ ] **I 체계** Git 루트 확인, `init: 과제 원본` commit
- [ ] **I 체계** install.py → init_work.py로 fde/work 생성
- [ ] **I 체계** 과제 폴더에서 Codex 시작, AGENTS 규칙 3개를 말하게 해서 로드 확인
- [ ] **I 제약** 금지 도구(Computer Use 등)·외부 전송·제출 경로를 state에 기록

### 15분 DISCOVERY 끝
- [ ] **I 목표** problem: 사용자·해결할 문제·성공 기준(측정 가능한 문장)
- [ ] **I 제약** problem: 만들 것·만들지 않을 것·제약·Unknown
- [ ] **C 예측** 데이터를 직접 열어 함정 후보를 내가 먼저 적고, AI 분석과 비교
- [ ] **I 의도** 질문 3~5개를 질문 카드 형식으로 보내고, 답 원문은 interview에 기록

### 30분 GATE1 합의
- [ ] **I 분해** skeleton ①~⑥ 행마다 입력→출력·함정·D-ID·REQ
- [ ] **I 검증** requirements의 REQ마다 P0/P1/P2·합격 문장·검증 명령·근거 D
- [ ] **I 의도** decisions D1~ 값까지 기록, 상태(확인/시범/Unknown) 구분
- [ ] **T 충족** 담당자 범위 승인과 시각을 state의 GATE1에 기록하고 commit

### 45분 GATE2 첫 결과
- [ ] **T 정확** 실제 입력→실제 출력이 한 번 끝까지 나옴
- [ ] **C 예측** 실행 전 예상을 대화에 남기고 결과와 대조
- [ ] **C 구조** "내가 이해한 구조: ①…⑥, 설정은 config" 한 줄을 확인받음
- [ ] **I 목표** 담당자에게 첫 결과를 보여 주고 성공 기준을 재확인
- [ ] **T 유지보수** `REQ-001: E2E v0` commit, state의 GATE2 기록

### 80~90분 구조 동결
- [ ] **T 유지보수** 단계별 함수 분리, 판정·순위는 순수 함수, 정책 값은 config(+D 연결)
- [ ] **C 구조** 입력→파일:함수→정책→출력을 내가 직접 추적해 decisions 예측·추적 칸에 기록
- [ ] **I 갱신** handoff·state에 `STATE=VERIFY, METHOD=④, D? 반영 중`

### 115분 VERIFY 끝
- [ ] **T 충족** P0 REQ 전부 통과, REQ별 commit
- [ ] **T 정확** 건수 보존식(배타 분류의 합 = 입력)·경계·회귀 테스트 통과
- [ ] **T 위험** 격리·오류 행을 버리지 않고 보여 줌, XSS·하드코딩 경로·바인딩 점검
- [ ] **I 체계** 같은 프롬프트 틀을 단계마다 재사용했나
- [ ] **C 근거** 주요 기준값마다 "왜·대안"을 물은 흔적이 있음

### 140분 새 기능 동결
- [ ] **I 분해** 새 요청을 설정 변경 / 단계 내부 / 경계 변경으로 분류해 반영·보류
- [ ] **I 갱신** 보류한 요청과 바뀐 결정을 새 D와 "대체됨→Dn"으로 기록
- [ ] **T 위험** 읽기 전용 감사 1회: 합의문↔코드↔테스트 대조

### 155분 GATE3 fresh run
- [ ] **T 완성도** 새 터미널에서 README_RUN 그대로 실행, 명령·exit code·HTTP 응답 기록
- [ ] **T 완성도** 과제가 요구한 문서 이름 그대로, 선택 이유·검증·한계 포함
- [ ] **C 예측** 한계·장애 시나리오를 내가 먼저 쓰고 AI는 보완만
- [ ] **I 검증** state의 GATE3 기록, `GATE3: fresh run passed` commit

### 170분 제출 직전
- [ ] **T 완성도** 제출 경로·파일명·저장 상태, 서버 터미널 유지
- [ ] **C 구조·근거** AI 없이 6줄 설명: 구조(①~⑥), 가장 큰 결정(Dn·대안·결과 차이), 남은 한계
- [ ] **I 갱신** handoff에 목표·완료 증거·미결 D·다음 3행동

## 3. 축별 최종 자가 진단 — 증거 위치로 확인

|---|---|---|---|
| T | 요구사항 충족 | requirements의 P0 상태와 테스트 로그 | |
| T | 기능적 정확성 | 정답 사례·경계·건수 보존 테스트 통과 | |
| T | 품질 위험·보안 | 격리 목록, 감사 결과, 바인딩·XSS 점검 | |
| T | 유지보수성 | 단계별 함수, config와 D 연결, REQ 단위 commit | |
| T | 제출물 완성도 | fresh run 기록, 지정 문서·경로 | |
| I | 목표 구체화 | problem의 성공 기준, 시연 후 재확인 | |

| I | 갱신·맥락 유지 | Q→D→REQ 연결, 대체 관계, state·handoff | |

## 4. 바로 감점되는 행동
- **I** "알아서 다 만들어 줘" 한 방 프롬프트, 담당자 답 요약·지어내기, 미응답을 승인으로 기록
- **I/T** 테스트가 실패하자 테스트나 기준을 고치게 두기
- **T** 데이터 행 조용히 삭제, 140분 이후 새 기능, 제출 경로 착오
- **C** 결과를 읽지 않고 "좋아, 다음" 반복, AI 용어를 이해 없이 서술형에 옮기기
