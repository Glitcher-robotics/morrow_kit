# 로컬 데이터 작업 규칙
- 첫 응답에서 현재 작업 폴더·Git 루트를 확인한다. 과제 폴더가 아니거나 Git 루트가 없으면 멈추고 알린다.
- 담당자 답을 받으면 같은 응답 안에서 interview Q-ID에 원문을, decisions.md에 D-ID(결정·영향 REQ·설정 키)를 추가한다. 기록 전에는 그 정책을 구현하지 않는다.
- 담당자 질문 초안을 만들기 전에 decisions.md를 확인한다. 이미 있는 결정은 다시 묻지 않고 D-ID를 인용한다.
- Computer Use·브라우저 자동화·화면 캡처를 쓰지 않는다. 화면 확인은 HTTP 응답과 테스트로만 한다.
- Codex·npm 전역 패키지를 업데이트·설치하지 않는다(`npm install -g`, `sudo` 설치 금지). 필요한 의존성은 표준 라이브러리로 대체하거나 사람 승인 후 프로젝트 안에만 둔다.
- `git add -A` 전에 `git status --short`로 `.codex/`·`.config/`·셸 설정 같은 홈 숨김 파일이 없는지 확인한다. 보이면 commit하지 말고 .gitignore부터 고친다.
- 웹 서버는 과제 README가 정한 포트를 쓴다. 정하지 않았으면 0.0.0.0:3000(시험 IDE 미리보기 포트)에 띄우고 `--port`로 바꿀 수 있게 한다. 띄운 뒤 그 포트로 HTTP 응답을 확인한다.
- 서버 시각은 UTC일 수 있다. 판정 기준 시각에 `now()`를 쓰지 않고 합의한 D(데이터 마지막 시각 등)를 쓰며, 기록의 시각에는 시간대를 붙인다.
- 과정 기록(problem·interview·decisions·requirements·skeleton·state·handoff)은 fde/work에만 둔다. docs/ 등에 같은 종류의 기록을 따로 만들지 않고, 과제가 지정한 제출 문서는 fde/work를 근거로 쓴다.
- D-ID는 `D1, D2…` 형식으로 쓴다. 정책이 걸린 구현 요청에 D-ID가 없으면 적용할 D를 먼저 확인하고, 해당 D가 없으면 구현하지 말고 질문 후보로 돌린다.
- REQ 검사가 통과하면 같은 응답에서 `git add <파일>`과 `REQ-xxx: METHOD ④ 요약 (Dn)` commit 명령을 제안하고 state의 마지막 commit을 갱신한다. Git 신원·전역 설정은 바꾸지 않는다.
- 체크포인트(45·80·115·140·155·170분)마다 `python fde/kit/status.py --intent` 결과와 fde/docs/SELFCHECK.md의 해당 체크리스트로 빈칸을 보고한다.
- 건수·순위·등급·테스트 수 같은 숫자는 방금 실행한 명령 출력에서 옮긴다. 기억·암산으로 쓰지 않고, 실행하지 않았으면 미실행이라고 쓴다.
- 문서에 쓰는 규칙·결정·결과에는 근거(파일:함수, Dn, Q-ID, 명령)를 붙인다. 붙일 수 없으면 `(추정)` 또는 Unknown으로 쓴다.
- 문서에 함수·설정 키·규칙 이름을 쓰기 전에 src에서 검색해 실제로 있는지 확인한다. 처음 쓰는 모듈·함수는 import·실행으로 존재를 확인한다.
- 결정을 새 D로 대체하면 옛 결정의 핵심 표현을 저장소 전체에서 검색해 남은 문장을 고치거나 "대체됨→Dn"으로 표시한다.
- 완료·통과 주장은 명령·exit code·핵심 출력과 함께 쓴다. "통과했습니다"만 쓰지 않는다.
- 프로젝트 README의 지정 구조·실행·데이터 사용·전달 정책이 우선한다. 기존 src와 사용자 변경을 보존한다.
- 시작/재개는 README와 fde/work의 problem/requirements/state/handoff부터 읽는다. 없으면 필요한 템플릿만 만든다.
- 새 세션의 첫 응답은 handoff 맨 위 요약 칸만 읽고 "STATE / 다음 3행동 / 이 세션이 맡을 범위"를 한 줄씩 되말한다. 기록 담당 세션이면 그 요지를 handoff의 `이어받기 시험:` 칸에 시각과 함께 남긴다.
- handoff 맨 위 요약 칸(목표·STATE·실행·핵심 결정·다음 3행동·이어받기 시험)은 `이름: 내용` 형식으로 20줄 안에 유지한다. 제목·문단으로 다시 쓰지 않고, 이력은 요약 아래나 git log로 보낸다.
- 여러 세션을 동시에 쓸 때 기록 파일(interview·decisions·requirements·state·handoff)을 고치는 세션은 사람이 지정한 1개뿐이다. 다른 세션은 맡은 코드·검토만 하고, 새 결정·질문은 "D 후보"로 보고만 한다. 같은 파일을 두 세션이 동시에 고치지 않는다.
- 필요할 때 fde/docs/METHOD.md와 STAGE_PROMPTS.md의 현재 STATE만 읽는다. 전부 순차 실행하거나 서류 자체를 목표로 삼지 않는다.
- 실제 사례·현재 처리·성공 기준부터 묻고 결과를 바꿀 핵심 질문 3~5개를 고른다. 받은 답 원문·출처는 interview Q-ID, 결정은 decisions D-ID에 참조한다.
- 예시·README의 업무 가정을 실제 정책으로 단정하지 않는다. 핵심 미확정은 질문하고, 범위·합격 기준의 실제 사람 승인 전 본 구현하지 않는다.
- requirements가 합격 문장의 원본이다. 독립 work 후보만 checks.json과 ID·우선순위·검사 명령을 맞춘다. 기존 src 프로젝트는 자체 검사·구조로 전달한다.
- skeleton에 읽기→정규화→정제→판정→순위/집계→표시의 입력·출력·정책 위치를 연결한다. 7 STATE와 6 METHOD는 별개이며 여섯 파일을 강제하지 않는다.
- 원본/표준 값을 추적하고, 같은 파일의 배타적 정상/격리/중복만 더한다. 경고를 재집계하지 않고 실제 반복·등급 미상을 임의 제거하지 않는다.
- 작은 실제 입력→출력을 먼저 확인하고 해당 REQ의 반례·경계·회귀를 검사한다. 판정·계산은 결정론적 코드로 수행한다.
- 관련 검사를 준비하고 실제 통과/실패·timeout·exit code·소스 일치를 남긴다. 테스트 통과를 고객 수용으로 기록하지 않는다.
- 사람의 실행 전 예상·직접 코드 추적·내 말 설명을 AI가 대필한 과거 행동으로 만들지 않는다. AI 초안은 사람이 대조한다.
- 정책 변경은 새 D-ID·대체 관계·영향 REQ·검사·handoff로 연결한다. 미확인 값을 구현 완료로 만들지 않는다.
- 기본 수정 범위를 좁히되 API/공통 검사 연결 수정은 이유·영향을 설명하고 확인된 범위에서 최소 변경한다.
- 같은 실패 3회면 반복 수정을 멈추고 원인·작은 재현·대안 2개를 보고한다. 새 의존성·외부 전송은 프로젝트의 승인 규칙을 따른다.
- champion은 promote.py로만 갱신하며 실패하면 기존 정상본을 보존한다. bundle은 work 밖의 파일을 자동 포함하지 않는다.
- 실제 전달 위치에서 새 프로세스로 실행하고 서버 준비/HTTP 응답과 유한 명령의 exit code를 구분한다.
- 180분 세션 예산은 참고값이다. 실제 마감과 필수 기능·정확성·큰 위험·최종 전달 시간을 보호하고 선택 기능·장식을 먼저 줄인다.
- STATE/GATE는 실제 근거로 기록한다. 내부 빈칸·Git 상태 때문에 전달을 지연하지 않고 실패·답 없음·미실행을 숨기지 않는다.
- 변경은 한 세션에서 한다. 가능한 읽기 전용 교차 검토를 하고 길어진 작업은 handoff의 목표·근거·다음 3행동으로 재개한다.
- 비밀·개인정보·원본 데이터·작업 로그를 공개하지 않는다. 허용된 자원·자동화·네트워크만 사용하고 해당 환경의 정책을 우회하지 않는다.
